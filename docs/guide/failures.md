# Failures and recovery

A failed connection should leave the user's draft in place and explain what they
can do next. Interact reports request failures automatically through `$server.error`.
Keep using ordinary bindings and Alpine actions:

```html
<button type="button" @click="$server.call('save')" :disabled="$server.busy">
  Save
</button>
<p role="alert" x-text="$server.error ? $server.error.message : ''"></p>
```

No catch callback is needed. The alert stays mounted so its text can be announced
when it changes. If you add padding or a background, put that styling on a wrapper
shown only while an error exists.

[Run the demo](/examples) and open `/playground`. The **Failure recovery** card
lets you simulate a server failure or expiry and keep typing afterwards.

## Keep the draft and offer a choice

Inside the owning island, add application-controlled recovery markup:

```php [Inside the island element]
<div x-show="$server.paused" x-cloak>
  <p>Automatic updates are paused. Keep your draft before leaving this page.</p>
  <?= $this->Form->control('draftExport', [
      'type' => 'textarea',
      'label' => 'Draft export',
      'readonly' => true,
      ':value' => '$server.exportDraft()',
  ]) ?>
  <button
    type="button"
    x-show="$server.error && $server.error.recovery === 'retry'"
    @click="$server.sync()"
    :disabled="$server.busy"
  >
    Synchronize latest draft
  </button>
</div>
```

Use the `x-cloak` stylesheet rule from [actions and feedback](/guide/actions).
Provide a normal reload link to your application's original page, or a sign-in
link generated by your application. Interact never invents a login URL.

After a failure:

1. Local editing continues. Automatic input, blur, and change requests stop.
2. Queued actions and pending debounce timers are cancelled.
3. For a `retry` failure, an explicit submit, action, or sync sends current draft
   values in a fresh request. It does not replay failed or cancelled work.
4. Other recovery categories require a fresh mount or application sign-in flow.

A connection failure or server error can happen **after a save completed**. Check
the operation's result before submitting again. Even a sync can run application
update hooks; decide what a fresh attempt means for your application's workflow.

`exportDraft()` returns formatted JSON containing all current writable state,
including values already synchronized but not saved. It excludes props, PHP-only
state, snapshots, and runtime metadata. Select and copy it manually. Writable
fields may contain sensitive values, so export only when the user chooses.
There is no automatic browser storage or restoration after reload.

## Understand the failure

`$server.error` contains `code`, a safe `message`, `status`, and `recovery`.
A status of null means no readable HTTP response is available.

| Code                  | Meaning                                                        | Recovery                                           |
| --------------------- | -------------------------------------------------------------- | -------------------------------------------------- |
| `snapshot_expired`    | The signed snapshot passed its lifetime                        | Reload                                             |
| `session_changed`     | The snapshot belongs to a different session                    | Reload                                             |
| `invalid_snapshot`    | Malformed, tampered, or wrong-scope snapshot                   | Reload                                             |
| `unauthenticated`     | Authentication is required (401)                               | Application sign-in flow                           |
| `csrf_failed`         | CakePHP rejected the security token (403)                      | Reload                                             |
| `forbidden`           | Current access is denied (403)                                 | Application decision                               |
| `invalid_request`     | Update input was rejected (400)                                | Correct input, then explicitly try again           |
| `server_error`        | Server returned a 5xx response                                 | Verify the outcome before another explicit attempt |
| `http_error`          | Another HTTP error status                                      | Application decision                               |
| `network_error`       | Fetch failed without a response                                | Verify the outcome before another explicit attempt |
| `unexpected_redirect` | The update redirected instead of returning its protocol        | Reload / check application authentication handling |
| `invalid_response`    | Invalid JSON, content type, envelope, identity, or root markup | Reload / check application logs                    |
| `client_error`        | The browser could not prepare or apply the update              | Reload / check browser diagnostics                 |

`none` means the runtime has no recovery to offer. Automatic requests remain
paused. It does not mean access can be restored by dismissing the message.

A valid HTTP 422 response is different: it renders application validation
feedback through `$errors` and `$server.errors` and does not pause interaction.

## Inspect an outcome in JavaScript

Advanced integrations can inspect an awaited call without an exception handler:

```ts
const result = await server.call('save');
if (!result.ok) {
  console.log(result.error.code);
}
```

`server` is the owning island bridge. Both `call()` and `sync()` settle with
`{ ok: true }` for an accepted render or `{ ok: false, error }` for a request
failure. An accepted render includes validation responses: inspect field errors
or your application's confirmation state to determine whether saving succeeded.

When an island disappears, waiting calls receive a `cancelled` outcome. The
runtime emits no new error UI for a removed island. Aborting browser fetch does
not cancel PHP execution.

For application-wide presentation, listen for the bubbling `interact:error`
event. Its detail contains the same failure fields as `$server.error`. It fires
once per failed request; blocked attempts do not repeatedly emit it. This event
is optional—ordinary templates can bind the error directly.

## Server integration

Update failures use safe, versioned JSON. The plugin subscribes to CakePHP's
`Exception.beforeRender` event, so middleware failures use the same contract
after normal exception logging. Other routes and application-handled error
responses retain their existing handling. Applications returning their own error
documents still receive safe status-based browser feedback; Interact does not
classify exceptions by parsing their message text.

No exception traces or raw error pages are inserted into island markup. The categories and recovery limits above also apply to application-owned middleware responses.

## Update existing error bindings

The development API previously exposed `$server.error` as a string. Replace
`x-text="$server.error"` with the null-safe message binding at the top of this
page. JavaScript calls now settle with a typed result; inspect `result.ok`
instead of relying on request failures rejecting the returned promise.
